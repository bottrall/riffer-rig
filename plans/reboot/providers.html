Providers

Which SDKs ship, how a model is chosen, and how each provider's credentials are asked for, stored and resolved. A provider added to riffer needs one table entry here.

Scope

Gemspec dependencies, the missing-SDK flow, model selection precedence, the recipe table, auth.json and the providers settings block, credential resolution, the /auth command, extension providers, provider-native tools. Files: riffer-rig.gemspec, lib/riffer/rig/recipes.rb, lib/riffer/rig/credentials.rb (reshaped), lib/riffer/rig/commands/auth.rb, lib/riffer/rig/sdk.rb (the installer).

Depends on: Session (per-session credentials, /model), Extensions (provider seam, Host ask). Depended on by: Loader (resolution), Hosts (the prompts).

Decisions

Dependencies

  • The gemspec hard-depends on riffer (~> 0.45.0), the openai gem, acp-sdk (once published; see Hosts: ACP) and the current zeitwerk and base64. One SDK covers OpenAI, OpenRouter and Azure OpenAI; Gemini needs no SDK (riffer uses net/http). Four of riffer's six providers therefore work on a bare gem install riffer-rig.
  • anthropic and aws-sdk-bedrockruntime are optional, installed on demand. The current hard dependency on anthropic is removed.
  • Provider breadth is an anti-goal: riffer's six providers plus whatever extensions register.

SDK table

Version constraints belong to riffer: each Riffer::Providers::Base subclass should expose its SDK gem name and requirement. Until riffer does, riffer-rig carries the mapping itself, as part of each recipe entry (sdk:), marked in code as an upstream candidate.

Missing SDK

  • Outside Bundler: the host offers Install the <gem> gem now? [Y/n] (host.confirm), then Gem.install(gem, requirement) plus Gem.clear_paths in-process under host.progress. Install then require works in the same process without a restart (verified).
  • Under Bundler (bundle exec, a project Gemfile): install cannot reach the load path, so print the exact gem '<name>' line to add and stop.
  • The same handler runs at onboarding and at any later /model switch. In headless mode the null host declines, the missing gem and the install line go to stderr, exit 2.

Selecting and switching the model

  • No baked-in default. The current DEFAULT_MODEL constant goes. With no model resolved, onboarding lists the providers from Riffer::Providers::Repository (Mock excluded, extension-registered providers included), asks for a model string, and writes the choice to the home settings.json.
  • Precedence, highest first: --model provider/name flag → RIFFER_MODEL env var → model in settings (project over home) → onboarding.
  • A model string without a provider prefix is rejected with a hint listing the registry's providers. No inference from credentials or name patterns. In headless mode this is exit 2.
  • /model provider/name switches for the current Session only (Session: /model); /model --save persists. It triggers the missing-SDK and credential flows as needed.

Recipe shape and the six built-in recipes

  • A recipe is data: a hash keyed by riffer's registry identifier with a help url, the sdk pair above, an optional chain: true, and a list of fields.
  • Field attributes: name (the member on Riffer.config.<provider> that receives the value; this is the delivery rule, no per-provider setter code), env (one or more env var names), secret (hidden input, stored in auth.json), required (only required fields are ever prompted), and an optional fallback: Proc tried after env and disk, before prompting: the single non-data escape hatch, per field.
  • chain: true tells the host to offer the SDK's own credential chain as the default before asking for a secret.
  • The table is core; the prompting is host work through the Host interface.

Resolution order

  • Per required field, first hit wins. Optional fields are resolved through the same chain minus the ask.
  • Resolved once per Session build, cached on the Session as credentials:, re-resolved on reload. A recipe that writes a file therefore takes effect in the running session without a restart; recipes never instruct the user to restart.
  • No validation. A pasted key is saved as-is; a bad key surfaces on the first request with the provider's own error. Probing would need per-provider code and break the one-entry goal.

Storage

  • ~/.riffer/auth.json (mode 0600, directory 0700) holds secret fields only, one typed entry per provider: 
    {"anthropic": {"type": "api_key", "api_key": "sk-ant-…"},
 "amazon_bedrock": {"type": "api_key", "api_token": "…"}}
    The type member follows pi and OpenCode and leaves room for an oauth type without reshaping the file. The current flat {"anthropic": "sk-…"} shape is replaced with no migration (the rename was already a clean cut).
  • A secret value may be a literal, a $ENV_VAR reference, or a !shell command whose stdout is the secret. That is how a keychain user plugs in security find-generic-password without rig owning keychain code. Expanded once per process when the Session is built.
  • Non-secret fields (endpoint, region, base_url) go to settings.json under "providers": {"azure_openai": {"endpoint": "…"}}, home scope by default.
  • No OS keychain. pi and OpenCode are 0600 JSON with typed entries; Codex made keyring opt-in; Claude Code's keychain-with-file-fallback is where its auth bugs live.

/auth

  • /auth lists every registry provider with a status: env, stored, chain or missing.
  • /auth <provider> re-runs the recipe (key rotation).
  • /auth remove <provider> deletes the auth.json entry and the providers block in settings.
  • Runtime-owned, so terminal and ACP share it. Not named /login, which implies OAuth.

Extension providers

  • The provider seam takes an optional recipe:: rig.provider(:jane, recipe: {url: …, fields: […]}) { JaneProvider }. Rig resolves it like a built-in and exposes values through Riffer::Rig.credentials(:jane); the provider class reads that when building its client. Built-ins get the same lookup plus the Riffer.config assignment.
  • No recipe: → generic fallback: one secret api_key with env <IDENTIFIER>_API_KEY.
  • Extension providers appear in onboarding, /model hints and /auth like built-ins, because all three read the registry.

Provider-native tools

  • Web search today, and code execution or file search later, arrive through riffer's provider seam. They are core (nothing an extension could add) and off by default.
  • Switched on per tool in settings: "tools": {"native": {"web_search": true}}. The Loader passes the switches to the Session, which enables the provider option only if the current provider supports it; otherwise nothing happens and no error is raised, so a provider change never silently changes what the agent can do.
  • On a provider without native search the user brings a third-party tool.

Headless

  • riffer -p never prompts. An unresolved required field prints the provider, each missing field with its env vars, the key URL and a hint to run riffer interactively, then exits 2. With --json it is the final {"type": "error"} line.
  • A missing optional SDK prints the gem and the install line, then exits 2.
