Extensions

An extension is a named registrar block. Requiring a file records it; Session.new runs it against a fresh per-Session registrar.

Scope

Riffer::Rig.extension, the extension object it returns, the per-Session Registrar and its eight seams, the command context, the handler and event vocabulary, the Host interface, error isolation, API versioning and the gem convention. Files: lib/riffer/rig/extension.rb, lib/riffer/rig/registrar.rb, lib/riffer/rig/command.rb (the ctx), lib/riffer/rig/host.rb.

Depends on: Session. Depended on by: Bundled (built on this API), Loader (runs discovery and reload through it), Hosts (implement the Host interface).

Decisions

The eight seams

CallDoesBacked by
rig.command name, description: { |ctx| }runtime slash command, works in every hostrig Command

rig.on(event) { |e| }lifecycle and loop handlersriffer on_message, tool runtime, guardrail phases
rig.provider(prefix, recipe: nil) { klass }custom provider prefix, process-wideRiffer::Providers::Repository.register (idempotent)

rig.setting key, default:declares a namespaced settings keyrig settings

Providers are the one process-wide seam by choice: providers are stateless and credentials are already per-Session via the client Proc. Two Sessions cannot map one prefix to different classes; accepted until a real host needs it. Providers are never unregistered on reload; re-registration is idempotent.

Commands

  • The block receives ctx with args (the text after the command name), session, host, settings (this extension's namespace), and helpers: say(text) emits a command_output event; prompt(text) sends a user turn to the model, so prompt templates are commands; ask and confirm forward to the host and return its answer (the null host declines).
  • Synchronous, one at a time, same rule as Session#prompt. A command that raises is caught and reported through notify; the Session stays usable.
  • Core commands (/model, /auth, /reload, skill activation) are built on the same Command type and appear in session.commands alongside extension commands.

Handlers and events

EventKindHandler may
session_start, session_end (reason: carries :new, :restore, :reload, :close)lifecycleacquire or release process-wide state
before_prompt, before_tool_call, before_requestvetoablereturn a replacement payload, or :block with a reason (becomes a tool error for a tool call, otherwise a host notify)
after_tool_call, after_response, turn_endobserve onlynothing; return value ignored
streampassthroughsee every riffer StreamEvent, unchanged
  • Event objects are immutable; transforms are return values, never mutations. Handlers run in load order; a vetoable handler's replacement feeds the next handler.
  • A raising handler counts as no veto and is reported through notify; the turn continues.
  • before_request fires between tool results and the next LLM call, not only at turn start. It is also where the Loader's reload check runs (Loader: reload).

Prompt sections

  • Named sections render after the base prompt in load order, before the environment block. A later registration of the same section name replaces the earlier one.
  • Sections are Procs evaluated every turn, so their content is always current without a reload. AGENTS.md and the skills listing are sections owned by their bundled extensions (:agents_md, :skills), so a user can swap either by registering the same name later without disabling the extension.
  • A section's text is appended as-is. A contributor that needs framing (AGENTS.md as "user-authored instructions that outrank the norms above") writes that framing itself; the base prompt names no contributor.

Settings seam

  • rig.setting :key, default: declares a key under the extension's namespace: settings.json["git"]["depth"], read as ctx.settings[:depth].
  • Project settings override home settings key by key. Core keys stay top level and an extension name cannot collide with a core key; the registrar rejects one that does.
  • Declared settings give a host a table to render; nothing else in core reads them.

Error isolation

  • The Loader wraps each require and the Session wraps each registrar block. A failure records {extension, error} on session.errors, skips that extension, and the host gets one notify. The rest of the extensions load.
  • At run time a raising handler or command is caught and reported the same way and the turn continues; a raising before_* handler counts as no veto.
  • Errors go to the host only, never into the model's context.

API versioning

  • The registrar surface is public API of riffer-rig under the release policy: 0.x minor bumps, a BREAKING CHANGES section, one minor of deprecation where feasible. No separate API number.
  • requires: on an extension is a Gem::Requirement string checked against Riffer::Rig::VERSION when the block is recorded; a mismatch is a load error reported like any other.

Gem convention and autoload

  • Convention, not a rule: gem riffer-rig-<name>, entry file lib/riffer/rig/<name>.rb that calls Riffer::Rig.extension("<name>"). A user adds it with require "riffer/rig/<name>" in a rig.rb.
  • Optional autoload: "extensions": {"autoload": true} in settings (off by default) makes the Loader require riffer/rig/extension from every gem in the bundle via Gem.find_files. A gem opts in by shipping that file.
  • Gem-packaged extensions never hot-reload; develop as a local file required from rig.rb, package when it settles.

Bundled items are extensions

  • read, write, edit, bash, skills, agents_md and mcp are each a named extension in the gem, built only on the seams above, loaded by the Loader before any rig.rb. Their content is in Bundled.
  • Disable: "extensions": {"disabled": ["mcp"]} in settings, either scope.
  • Replace: register a tool or command under the same identifier from a later extension. Later wins; the override is logged through notify at info level.
  • Embedders reference them as Riffer::Rig.bundled(:read); Riffer::Rig.bundled with no argument returns all seven in load order.
