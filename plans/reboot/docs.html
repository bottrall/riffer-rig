Docs

Where every user-facing line of this plan ends up: riffer's approach, in full.

Scope

The README, the docs/ guides, a port of riffer's docs-site/ generator, the gh-pages deploy and the custom domain. This unit is consumed by every build PR (each moves its user-facing text here) and finished by one docs PR that creates the site. It depends on every other unit being described; it changes no code.

README shape

  1. Title and tagline. "riffer, in your terminal and in your process." One paragraph from the thesis: a general-purpose agent for Ruby developers who want to own their harness; runs in the terminal and inside any Ruby process; extend it in Ruby; ships the coding toolkit as its default bundle. The current "dead-simple terminal coding agent" line is replaced here, not before.
  2. Requirements. Ruby >= 4.0.
  3. Installation. gem install riffer-rig gives the riffer executable; which providers work out of the box and which SDKs are installed on demand.
  4. Usage. riffer, first-run onboarding, riffer -p, riffer acp, the shared flags, the runtime and terminal commands.
  5. Authentication. Env vars, auth.json, /auth, a pointer to the per-provider pages.
  6. Configuration. The two settings scopes, every core key with one line each, RIFFER_MODEL, AGENTS.md, skills, MCP servers.
  7. Extending. A ten-line rig.rb example and a pointer to the guide.
  8. Embedding. The three-line Loader.session(...).ask(...) example and a pointer to the guide.
  9. Documentation. The guide list below, each linked to https://riffer.bottrall.dev/guides/<slug>/ with its one-line description, plus "the guide sources are in docs/" and how to preview the site locally.
  10. Development. The bin/ table, unchanged in form, gaining bin/docs and bin/plans rows.
  11. Releasing. As today.
  12. Contributing, License, Maintainer. As today.

The docs-site generator

  • Port riffer's docs-site/ (in the janeapp/riffer repo) as it stands: build.rb, check.rb, layout.html.erb, index.html.erb, site.css, landing.css, copy.js, favicon.svg, 404.html, manifest.yml. Names, wording and the landing copy change to riffer-rig; the build logic does not. The build fails on any mismatch between manifest.yml and docs/**/*.md; check.rb validates every internal link and anchor.
  • manifest.yml holds the four groups above in that order, with source, slug, description per page and featured: true on Getting Started.
  • Dev dependencies added to the Gemfile, as riffer has them: kramdown, kramdown-parser-gfm, rouge. Plus rdoc for the API reference at /api/, built by an RDoc::Task over README, CHANGELOG, LICENSE and lib/**/*.rb into _site/api.
  • Rake tasks, defined once: docs:site (build into _site/), docs:check (build then check), docs:serve (build then ruby -run -e httpd _site -p 8000), rdoc, and docs = docs:site + rdoc. bin/docs delegates to rake docs and forwards arguments; the README Development table gains its row. _site/ is git-ignored.
  • A CNAME file containing riffer.bottrall.dev is added to the asset list so it lands in _site/ on every build.

Deploy

  • A docs job in .github/workflows/publish.yml, needs: release-please and gated on release_created == 'true' like the publish job (the same trigger riffer uses): checkout, ruby/setup-ruby with bundler-cache, bin/docs, then JamesIves/github-pages-deploy-action pinned by commit SHA with branch: gh-pages and folder: ./_site; permissions contents: write.
  • The site therefore updates only on a release, so it always documents a published version. The version string in the layout comes from Riffer::Rig::VERSION.
  • Repository settings (human, once): Pages source = gh-pages branch, root; custom domain riffer.bottrall.dev; enforce HTTPS. DNS (human, once): a CNAME record for riffer under bottrall.dev pointing at bottrall.github.io. Until the domain resolves, the site is reachable at the default project URL.

When the docs are written

  • Each build PR moves its topic's user-facing text into README or the guide its Enshrines-into row names, creating the guide file (and its manifest entry, once the generator exists) if it does not exist yet. A guide may be short for a while; it is never absent.
  • The docs PR itself (the last unit) ports the generator, writes OVERVIEW.md and GETTING_STARTED.md, rewrites the README top matter to the thesis, adds the workflow job and deletes this file. If it lands before every other unit, later build PRs still add to the guides as above.
  • Both the plan PR and every docs PR are titled docs: … and never release.
