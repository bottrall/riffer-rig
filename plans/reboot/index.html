riffer-rig reboot: building plan

Everything decided for the post-hiatus reboot, regrouped so that whoever builds a unit reads one file. Temporary: each build PR deletes what it enshrines, and this directory is gone when the reboot is built and documented.

Thesis

A general-purpose agent for Ruby developers who want to own their harness. It runs as a terminal agent and, because the runtime is separate from the terminal, it also runs inside any Ruby process: a Rails app, a script, a job. You extend it in Ruby: tools, commands, providers and hooks are ordinary Ruby classes on riffer's primitives, and the same objects work whether the host is the terminal or your app. It ships with a coding toolkit (read, write, edit, bash) as the default bundle because a shell and file access are the most efficient way to get almost any task done, but the prompt gives it no coding identity. Built and maintained by riffer's lead maintainer as a personal MIT project, so the framework grows whatever the agent needs. It does not compete on provider breadth, on polish with Claude Code, as a hosted product, or for non-Ruby developers.

Primary audience

Ruby developers who want to own their harness. They would rather extend a small agent in the language they already write than accept Claude Code's or Codex's workflows. Every unit below asks: does this serve them?

The two claims over pi, OpenCode, Claude Code and Codex

  1. Runs in your Ruby process. None of the four can be embedded from Ruby; all give Ruby a subprocess with JSONL, HTTP or RPC.
  2. Extend it in Ruby. pi offers in-process code extensions in TypeScript; nobody offers them in Ruby.

Riffer's toolkit (evals, guardrails, tracing, MCP client) and provider choice are true but are not the pitch.

Two pillars, one boundary

Extension-in-Ruby and in-process embedding are co-equal. They do not conflict as long as the runtime/terminal boundary holds. Three seams keep that boundary honest, and each has a home in this plan:

  • extensions that touch the UI go through a host interface the terminal implements and an embedding host implements differently or ignores (Extensions: Host interface);
  • extension discovery (scanning config and project directories) lives in the Loader; the runtime only accepts registered objects (Loader: discovery);
  • global state (riffer registries, config singletons) allows several isolated agents in one process (Session: per-session credentials).

Discipline: the runtime assumes no TTY, and no further embedding accommodation is made until a real host exists. Jane is the obvious first host.

Anti-goals

  • Not competing on provider breadth.
  • Not competing on polish with Claude Code: no desktop app, IDE plugin or subscription login.
  • Not a hosted product or business.
  • Not serving non-Ruby developers; they get ACP or a subprocess.
  • No permission model for tool execution: the tool trusts the model.

The core-versus-extension rule

Everything in the project is one of four things. Ask in order; the first "yes" wins.

  1. Core: is it something an extension cannot do, or something every host needs in exactly the same form? Then it is core.
  2. Host: is it about how one front-end drives the runtime? Then it belongs to that host. The terminal is one host; the headless printer, the ACP adapter and a Rails app are others.
  3. Bundled: is it the coding toolkit (read, write, edit, bash), or a convention at least two of pi, OpenCode, Claude Code and Codex already share (same files read or same wire format)? Then it ships in the gem, is built only on the extension API, and the user can disable or replace it.
  4. Third-party: everything else: ordinary Ruby extensions people write and publish themselves.

  • Provider-native tools are core and off by default. Web search today, code execution or file search later, arrive through riffer's provider seam and are switched on in settings so a provider change never silently changes what the agent can do.
  • Standards never touch core. A new convention only asks "is the extension API rich enough to express this?" If not, that is a seam to add. The Agent Client Protocol is not a bundled item; it is a second host.
  • Core lives in riffer-rig first. Extract to riffer only when a second riffer agent needs the same thing. During the reboot riffer is not changed at all; in-gem workarounds are marked in code as upstream candidates.

Names

The name is riffer-rig. A player's rig is the whole setup they own and tweak: instrument, pedals, amp. It is the music word for "harness", so it restates the thesis without a jargon word, and it says nothing about coding or terminals, so it survives the runtime/CLI split. The rename has been applied; these are the names every unit uses.

Already in place

Three decisions were applied before this plan was written and get no unit file. They constrain every build PR:

  • Release policy. SemVer in 0.x; release-please over conventional-commit PR titles (linted in CI); feat and feat! bump minor, fix bumps patch, chore/docs/ci/refactor/test never release; RubyGems Trusted Publishing from publish.yml; riffer pinned ~> 0.45.0; Ruby >= 4.0. Every break is a feat! with a BREAKING CHANGES entry and, where feasible, one minor of deprecation. See README "Releasing".
  • Rename. The tree is already lib/riffer/rig/; riffer-rig 0.1.0 (the pre-reboot CLI) is on RubyGems. Nothing was ever published as riffer-code and nothing migrates from it.
  • bin/ over rake. Every chore is a rake task defined once; bin/ scripts only delegate. New chores (docs, plans) follow the same layering.

How this plan is consumed

  • The text is frozen. Wording never changes after the plan PR merges. Discussion happens on the tickets each file cites under Provenance, or in build PRs.
  • PRs delete what they enshrine. A build PR that lands a topic deletes that <section class="topic"> in the same PR and moves anything user-facing into README or a docs/ guide (Docs says which). A unit file goes when no sections remain; plans/reboot/ goes when no files remain; this index goes last. The plan only ever shrinks.
  • A wrong section is deleted anyway. If a PR discovers the plan is wrong, it records the deviation in the PR description and deletes the section. The code is then the truth.
  • Diagrams are prose. An inline SVG is deleted with its section.
  • Nothing here is a permanent record. The tickets are. This directory is served locally by bin/plans at http://localhost:8001/reboot/ and also works from file://.
