Session

The runtime. A plain Ruby object every host drives the same way.

Scope

Riffer::Rig::Session and the value objects around it: Turn, the rig-level events, Command, the null host. It wraps one Riffer::Agent built from a per-instance Riffer::Agent::Config. It assumes no TTY, scans no disk and accepts registered objects only. Files: lib/riffer/rig/session.rb, lib/riffer/rig/events.rb, lib/riffer/rig/command.rb, lib/riffer/rig/host.rb (the duck's documentation and NullHost), lib/riffer/rig/turn.rb.

Depends on: riffer only. Depended on by: every other unit. The registrar it runs extension blocks against is specified in Extensions; this file covers what the Session does with the result.

Decisions

The Session object and its contract

  • Session.new(...) builds a per-instance Riffer::Agent::Config; there is no class-level agent DSL. Two Sessions in one process share nothing but the process-wide extension registry and riffer's provider repository.
  • One prompt at a time per Session. A second prompt while one is running raises. Parallelism means more Sessions, in more threads.
  • The Session never renders, never prints, never reads the filesystem. Anything a host needs becomes a Session feature so embedders get it too.
  • The constructor takes everything as keywords: model:, credentials:, extensions:, tools:, settings:, pricing:, host:, cwd:, name:, instructions:, max_steps:, snapshot:. All optional except model:; the Interfaces table gives each one's meaning.
  • The current implementation's CodingAgent class-level DSL, its Settings.model lookup at class-definition time and its AGENTS.md reading inside instructions all go. Model, tools, skills backend and instructions are supplied per instance.

Prompting and the loop

  • prompt(text) runs one turn on the calling thread. With a block it yields every event as it happens; without one it returns an Enumerator. It returns when the turn ends.
  • ask(text) drains prompt and returns a Turn: text, stop_reason, tool_calls, usage, cost. The headless host and embedders build on it; the terminal builds on the stream.
  • max_steps: maps to riffer's config.max_steps. No default limit in the REPL; hitting it ends the turn with stop reason max_steps.
  • Stop reasons are riffer's finish reasons plus max_steps and cancelled: stop, length, context_window, content_filter, malformed_output, max_steps, cancelled, error. Hosts map them to exit codes or UI; the Session only reports them in turn_end.
  • The loop itself is riffer's. riffer-rig adds nothing to it beyond the callbacks the events, cancel and reload sections describe.

System message assembly and the base prompt

The base prompt is a short, task-neutral text owned by the Session. It names the agent, says it is general purpose and works through whatever tools it has, and states three norms. It lists no tools and names no conventions (not AGENTS.md, not skills, not slash commands; each introduces itself when present, so a Session with the bundle off says nothing untrue). It is a heredoc in the Session's agent definition, produced by a small pure function of the name. Wording is illustrative; the decision fixes the identity shape and the three norms, not the sentences:

You are {name}, a general-purpose agent. You work by using the tools you have
been given; each tool describes what it does and when to use it.

- Verify with your tools before answering. When a tool can settle a question,
  look rather than guess.
- Do what was asked, and all of what was asked. Do not widen the scope, tidy
  nearby things, or add extras that were not requested.
- Be concise. Lead with the outcome; do not restate the question.

Events

The stream a host consumes is riffer's StreamEvents unchanged, plus a few rig-level events. Every host renders this one stream; the ACP adapter is the only place it is mapped to another vocabulary, and the headless host prints it as NDJSON verbatim.

Event objects are immutable value objects (Data). Each has to_h; the event type name is the class name in snake_case, which is what the NDJSON "type" field carries. Extension handlers that observe the loop (after_tool_call, after_response, turn_end, stream) receive these same objects; the vetoable before_* hooks are described under Extensions: handlers.

Cancel

  • cancel is thread-safe and callable mid-turn from any thread. It sets a flag and installs, via riffer's on_message callback, a throw of :riffer_interrupt with reason :cancelled at the next message boundary. riffer then heals orphaned tool calls and emits its Interrupt event; the turn ends with stop reason cancelled.
  • The bundled Bash tool reads the flag to kill its running subprocess early instead of waiting for the message boundary.
  • Implemented inside riffer-rig with no riffer change; marked in code as an upstream candidate (a cancel token on riffer's run loop).

Commands

  • The runtime owns slash commands as registered objects. commands lists them (name, description); run_command(name, args) runs one, synchronously, one at a time, under the same rule as prompt.
  • Runtime commands in the reboot: /model (this file), /auth (Providers), /reload (installed by the Loader), skill activation (Bundled), and every command an extension registers. They work identically in the terminal, in headless mode and over ACP, which advertises them as available_commands.
  • Host-lifecycle commands stay in the host: /exit, /quit, /resume, /new replace or end the Session the terminal drives, so they live in Terminal.
  • A command block receives a ctx (Extensions: commands) whose say emits command_output and whose prompt sends a user turn to the model.

Per-session credentials

  • credentials: is a hash keyed by provider identifier holding the resolved values for that Session (see Providers: resolution). The Session never resolves them itself.
  • Session#prompt marks the Session as current for the calling thread (a thread-local). At boot riffer-rig installs one Proc per provider into Riffer.config.<provider>.client; riffer resolves that Proc on every LLM call, and it returns a client built from the current Session's credentials. Two Sessions with different keys run in parallel threads.
  • Riffer::Rig.credentials(:identifier) reads the current Session's values; extension providers call it when building their client.
  • Riffer.configure remains a fallback a host may use at its edge; the shipped hosts do not.
  • Contained in riffer-rig, marked as an upstream candidate (a per-agent provider option in riffer).

/model

  • /model provider/name switches the model for the current Session only, keeping conversation history. riffer's model setting accepts a Proc, so no agent rebuild is needed; the Session stores the override and the Proc reads it.
  • A model string without a provider prefix is rejected with a hint listing the registry's providers. No inference from credentials or name patterns.
  • Switching to a provider whose SDK is missing or whose credentials are unresolved triggers the host-side flows in Providers through the Host interface; the null host declines and the command reports the failure.
  • Persisting is a separate explicit act: /model --save writes the choice to the home settings.json. The settings file only changes when asked.
  • The override survives rebuild and is part of the snapshot.

Token tally and pricing

  • The Session keeps a running tally of token usage across turns and prices it with the pricing: table it was given (the models block of settings, USD per million tokens; missing pricing means cost is nil, never zero). Turn#usage and Turn#cost and the turn_end event expose the per-turn numbers; tally exposes the totals.
  • The tally is kept across rebuild. It is not stored in the snapshot: assistant messages carry token_usage, so a restored Session re-sums it, and pricing comes from today's settings, never the file.
  • The existing TokenTally module is the seed; it moves behind the Session.

Snapshot

  • to_h returns a plain hash; Session.new(snapshot: hash, ...) takes one back. The Session never touches disk; the Loader's store (Loader: session store) does.
  • Contents: id (UUIDv7 minted at creation; the same id is the picker row, the -r <id> argument and the ACP sessionId), messages (riffer Messages::Base#to_h, restored with Messages::Base.from_hash and seeded via Riffer::Agent.new(session:)), model (the /model override, if any), skills (activated skill names from riffer's Skills::Context).
  • Not stored: the tally, and any registration (tools, commands, handlers, prompt sections, MCP servers). Registrations are rebuilt from the extensions: given at restore time, using the same internal registrar builder as rebuild; there is no second restore path.
  • History is data, the present wins. Nothing blocks a restore: a tool_call for a tool that no longer exists is just text to the model now; orphaned tool calls at the tail (crash or kill mid-turn) are healed on load with a synthetic "interrupted" tool result, the same thing riffer does on cancel; skill activations re-apply by name and a missing skill is dropped silently; the saved model applies only if that provider has credentials in credentials:, otherwise the given model: is used and the host gets one notify.
  • A restored Session emits session_start(reason: :restore).

rebuild

  • rebuild(extensions:, settings:) is the primitive behind hot reloading: emit session_end(reason: :reload), build a fresh registrar from the given extension list aside, swap it in atomically, emit session_start(reason: :reload). If building the new registrar raises, nothing on the Session changes and the error propagates to the caller (the Loader turns it into one notify).
  • Kept across a rebuild: message history, tally, the /model override (the re-read settings model does not clobber it), the Session's identity and its host reference. Rebuilt from scratch: tools, commands, prompt sections, handlers, skills sources, declared settings. MCP servers restart, except a server whose name, command and args are unchanged keeps its live connection. Extension process-wide state is released in session_end and re-acquired in session_start. Providers are process-wide and are never unregistered; re-registration is idempotent.
  • Callable only between steps. From inside a handler or command it raises.
  • Embedders without a Loader call rebuild themselves, for example after their app's own code reload. They get no file watching and no /reload, correctly, since the runtime knows no filesystem conventions.
