Loader

Every filesystem convention in one place. Builds a Session for a working directory; the runtime never learns where anything lives.

Scope

Riffer::Rig::Loader: discovery of rig.rb files and their trust, settings and credential resolution, the reload check and /reload, the session store and resume, and the one-call constructor Loader.session. Used by the terminal, the headless host and the ACP server; a Rails host skips it and registers objects directly. Files: lib/riffer/rig/loader.rb, lib/riffer/rig/settings.rb (reshaped), lib/riffer/rig/trust.rb, lib/riffer/rig/store/jsonl.rb, lib/riffer/rig/commands/reload.rb.

Depends on: Session, Extensions, Bundled, and the credential resolution rules in Providers. Depended on by: the three shipped hosts.

Decisions

Building a Session

Loader.session(cwd:, host:, **keywords) performs these steps in order and returns a Session. Loader.new(cwd:, host:, store:) exposes the same steps to a host that needs the Loader object afterwards (for reload and resume).

  1. Read ~/.riffer/settings.json then <cwd>/.riffer/settings.json; merge key by key, project winning. Apply the flag and env overrides the host passed (model: from --model or RIFFER_MODEL).
  2. Resolve credentials for the selected model's provider (Providers: resolution), asking the host when allowed.
  3. Take the bundled extensions minus extensions.disabled and the strip keywords.
  4. Load ~/.riffer/rig.rb, then <cwd>/.riffer/rig.rb if trusted, recording tracked files. Append every extension recorded during those loads, in record order.
  5. Construct the Session with model:, credentials:, extensions:, tools:, settings:, pricing:, host:, cwd:, max_steps:, and snapshot: when resuming.
  6. Install the Loader-owned pieces on the Session: the /reload command, the before_request reload check (unless reload is manual), and the store observer on on_message.

If model: is still unresolved after step 1 (no flag, no env, no setting) the Loader asks the host to run onboarding (Hosts: terminal); the null host declines and the Loader raises the configuration error the headless host maps to exit 2.

Discovery

  • Two files, in this order: ~/.riffer/rig.rb, then <cwd>/.riffer/rig.rb. Plain Ruby, evaluated with load. They require gems, require_relative local files, or call Riffer::Rig.extension inline. Ruby's require order is the load order.
  • No directory scanning, no manifest, no settings list of extensions. What is required is what loads.
  • With "extensions": {"autoload": true} (default false) the Loader additionally requires riffer/rig/extension from every gem in the bundle via Gem.find_files, before the two files.
  • The strip keyword extensions: false (--no-extensions) skips both files and autoload; the bundle still loads.

Trust

  • The home file is always trusted. The first time a project .riffer/rig.rb is seen for a cwd, the Loader calls host.confirm with the path; the answer is stored by absolute path in ~/.riffer/trust.json ({"<path>": true | false}) and not asked again.
  • The null host declines, so headless and ACP sessions load home config only until a terminal session trusts the project. A declined project file is skipped silently and never re-asked until its entry is removed from trust.json.
  • A project rig.rb that appears mid-session (see reload) goes through the same confirm.

Settings

  • Two scopes, same file name: ~/.riffer/settings.json and <cwd>/.riffer/settings.json. Project overrides home key by key; nested extension namespaces merge the same way.
  • Core keys, all top level and all optional: model, reasoning, models (pricing table), reload, extensions (disabled, autoload), sessions (save), providers (non-secret provider fields), mcp (servers), tools (native, the provider-native tool switches). Extension names cannot collide with these.
  • The current Settings module's model-options logic (cache control, reasoning levels per provider) is kept and moves behind the Loader, which passes the result to the Session as riffer model_options.
  • Settings are re-read on reload; a settings change is itself a reload trigger.

Credentials

  • The Loader resolves every required field of the selected provider's recipe (env → auth.json → fallback Proc → host.ask(secret: true)), writes what the host answered to auth.json or the providers settings block, and passes the resolved values to the Session as credentials:. The rules and file formats are in Providers.
  • Resolution happens once per build and again on reload; $VAR and !cmd references in auth.json are expanded at that moment and cached on the Session.
  • Switching provider with /model resolves the new provider's fields the same way through the Loader-installed command context.

Reload

Scope

  • Reloaded: both rig.rb files, every local file they require or require_relative (under ~/.riffer or the project), settings.json in both scopes, auth.json, and trust status (a newly appearing project rig.rb goes through host.confirm).
  • Not reloaded: extension gems (riffer-rig-*), riffer-rig's own code (its Zeitwerk loader stays non-reloadable), riffer. Skills and AGENTS.md need no reload: their sections are evaluated per turn.

Triggers

  • Automatic: at every before_request boundary (between tool results and the next LLM call, not only at turn start) the Loader stats the tracked file set; any mtime change, or a tracked rig.rb appearing or disappearing, reloads. An agent that edits its own extension mid-turn sees the new tool on its very next request. A one-turn riffer -p benefits the same way.
  • Manual: /reload, a runtime command installed by the Loader; always reloads and re-discovers the file set.
  • No watcher thread, no listen dependency; the check runs on the prompting thread at a boundary where no handler is mid-flight, so no lock.
  • Core setting "reload": "auto" | "manual", default auto, project overrides home, also the Loader keyword reload:. Manual keeps /reload and Session#rebuild and drops the automatic check.

Mechanism

  1. On first load the Loader diffs $LOADED_FEATURES around loading each rig.rb; new entries under ~/.riffer or the project are the tracked files, gem paths dropped. The rig.rb files themselves are tracked too, so a newly added require is picked up from that reload on.
  2. On reload it deletes those entries from $LOADED_FEATURES and loads each rig.rb again, so plain require/require_relative re-execute with no author-side convention.
  3. Classes are reopened in place, not removed: edited and added methods take effect; deleted methods and renamed constants linger until restart (the one documented limit).
  4. Riffer::Rig.extension("name") records into the process registry keyed by name, so re-execution replaces the block rather than appending a duplicate.
  5. Settings, credentials and trust are re-read, then session.rebuild(extensions:, settings:).

Why not hot module replacement: Ruby's require keeps no dependency graph between files and extension blocks, and "later wins" ordering must be replayed anyway, so partial replacement would preserve only block locals at the cost of a second code path. Rejected: per-scope re-execution and TracePoint-based per-extension replacement.

Failure

  • The new registrar is built aside; nothing on the Session changes until it is complete. If a rig.rb itself raises, the reload is abandoned, the live registrar stays, the host gets one notify, and the mtime snapshot still advances so the check does not retry every request.
  • A single extension block failing follows the standard rule: skipped and reported, the rest swap in.
  • Errors go to the host only, never into the model's context.

Known limits

  • Reopened classes keep deleted methods and stale constants until restart.
  • Gem-packaged extensions do not reload.
  • Two Sessions in one process share the process-level extension registry and providers; a reload in one does not rebuild the other.

Session store and resume

  • The Loader takes a store: collaborator, mints the Session id, appends entries as they land, restores snapshots, and prunes nothing. Hosts never see the store; they only choose which session to drive. Embedders without a Loader get no store.
  • Store duck: append(id, entry) (one entry hash, in order), read(id) (entries in order), list(cwd: nil) (header entries, optionally filtered by cwd), delete(id). A Rails host implements it over its own tables or skips the Loader and serialises the snapshot directly.
  • Entries: header (schema_version, id, cwd, created_at, model, riffer_rig_version, riffer_version, title = the first user prompt truncated to one line), message (a riffer message to_h, appended via session.on_message), model (each /model change), skill (each activation). Restore folds entries into a snapshot: last model wins, skill accumulates, message is the history. New entry types can be added without a schema bump.
  • Default store: JSONL at ~/.riffer/sessions/<cwd-slug>/<uuid>.jsonl, one entry per line, appended with File.write(mode: "a"). Zero dependencies, cat- and jq-able; a crash loses at most one line. The slug directory makes per-project listing a directory read, but the header's cwd is the truth, not the path. SQLite is not in core; it belongs in an extension gem such as riffer-rig-sqlite.
  • Restore reads the entries, folds them, and builds the Session with snapshot: plus today's extensions from rig.rb; the Session's restore rules (heal orphaned tail tool calls, saved model only with credentials, missing skills dropped) apply. Nothing blocks a resume.
  • Selection the Loader offers hosts: continue(cwd:) (most recently updated session whose header cwd matches, or nil), resume(id) (or nil if unknown), list(cwd:, all: false) for a picker, delete(id).
  • Policies: every Loader-built session is saved, including -p one-shots; opt out per run with store: nil (--no-save) or globally with "sessions": {"save": false}; keep forever, delete only from the picker; titles are the first prompt, no model call; scoped per cwd by default.
  • Deliberately not built: branching or a session tree, automatic pruning, generated or user-set titles, cross-project search, a riffer sessions subcommand.
