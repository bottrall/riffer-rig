Loader

Every filesystem convention in one place. Builds a Runtime for a working directory; the runtime itself never learns where anything lives.

Scope

Riffer::Rig::Loader: discovery of rig.rb files and their trust, settings and credential resolution, the reload check and /reload, the session store and resume, and the one-call constructor Loader.runtime. Used by the terminal, the headless host and the ACP server; a Rails host skips it and registers objects directly. Files: lib/riffer/rig/loader.rb, lib/riffer/rig/settings.rb (reshaped), lib/riffer/rig/trust.rb, lib/riffer/rig/stores/ (base.rb, jsonl.rb), lib/riffer/rig/commands/reload.rb.

Depends on: Runtime, Extensions, Bundled, and the credential resolution rules in Providers. Depended on by: the three shipped hosts.

Decisions

Building a Runtime

Loader.runtime(cwd:, host:, **keywords) performs these steps in order and returns a Runtime. Loader.new(cwd:, host:, store:) exposes the same steps to a host that needs the Loader object afterwards (for reload and resume).

  1. Read ~/.riffer/settings.json then <cwd>/.riffer/settings.json; merge key by key, project winning. Apply the flag and env overrides the host passed (model: from --model or RIFFER_MODEL).
  2. Resolve credentials for the selected model's provider (Providers: resolution), asking the host when allowed.
  3. Take the bundled extensions minus extensions.disabled and the strip keywords.
  4. Load ~/.riffer/rig.rb, then <cwd>/.riffer/rig.rb if trusted, recording tracked files. Append every extension recorded during those loads, in record order.
  5. Construct the Runtime with model:, credentials: (provider → resolved field values), extensions:, tools:, settings:, pricing: (model → Settings::Pricing entries), host:, cwd:, max_steps:, and snapshot: when resuming.
  6. Install the Loader-owned pieces on the Runtime: the /reload command, the before_request reload check (unless reload is manual), and the store observer on on_message.

If model: is still unresolved after step 1 (no flag, no env, no setting) the Loader asks the host to run onboarding (Hosts: terminal); the null host declines and the Loader raises the configuration error the headless host maps to exit 2.

Discovery

  • Two files, in this order: ~/.riffer/rig.rb, then <cwd>/.riffer/rig.rb. Plain Ruby, evaluated with load. They require gems, require_relative local files, or call Riffer::Rig.extension inline. Ruby's require order is the load order.
  • No directory scanning, no manifest, no settings list of extensions. What is required is what loads.
  • With "extensions": {"autoload": true} (default false) the Loader additionally requires riffer/rig/extension from every gem in the bundle via Gem.find_files, before the two files.
  • The strip keyword extensions: false (--no-extensions) skips both files and autoload; the bundle still loads.

Enshrined in #126, with the Interfaces rows Files (rig.rb files, trust.json) and Settings keys owned here (extensions.autoload): the Loader runs ~/.riffer/rig.rb, then <cwd>/.riffer/rig.rb if trusted, each with load wrapped in the error isolation of #114, and appends every extension the loads recorded, in registry record order, after the bundle. Riffer::Rig::Trust (lib/riffer/rig/trust.rb) reads and stores trust.json; user-facing text is in docs/EXTENSIONS.md (The rig.rb files, Gem extensions) and docs/CONFIGURATION.md. Deviations. The autoload files are executed with load rather than require, so a second Loader.runtime in the same process re-records the gem extensions — with require the second build would drop them, since the require no-ops and nothing is re-recorded. A host that cannot confirm is never asked and its decline is not stored (see the note under Trust). The extensions a failing file recorded stay in the process registry; the build does not append them, and the failure is one notify rather than a runtime.errors entry, which only the Runtime owns. Loader#tracked_files records the local files the loads required — the rig.rb files included, gem paths dropped — for the reload check of #132.

Trust

  • The home file is always trusted. The first time a project .riffer/rig.rb is seen for a cwd, the Loader calls host.confirm with the path; the answer is stored by absolute path in ~/.riffer/trust.json ({"<path>": true | false}) and not asked again.
  • The null host declines, so headless and ACP sessions load home config only until a terminal session trusts the project. A declined project file is skipped silently and never re-asked until its entry is removed from trust.json.
  • A project rig.rb that appears mid-session (see reload) goes through the same confirm.

Enshrined in #126, with the Interfaces row Files for trust.json: the Loader calls host.confirm("Trust <path>?") only when host.capabilities includes :confirm, stores the answer by absolute path in ~/.riffer/trust.json through Riffer::Rig::Trust, and loads the project file only on a stored true. Bullet 3's appearing-mid-session trigger is #133's; the confirm it goes through is this code. Deviation: a host that cannot confirm (the null host, headless, ACP) is never asked and its decline is not stored — with the decline stored, "load home config only until a terminal session trusts the project" could never happen, since the terminal session would see the false entry and never ask. The ask-once rule holds for hosts that can confirm: a stored false is skipped silently and never re-asked until the entry is removed.

Settings

  • Two scopes, same file name: ~/.riffer/settings.json and <cwd>/.riffer/settings.json. Project overrides home key by key; nested extension namespaces merge the same way.
  • Core keys, all top level and all optional: model, reasoning, models (pricing table), reload, extensions (disabled, autoload), sessions (save), providers (non-secret provider fields), mcp (servers), tools (native, the provider-native tool switches). Extension names cannot collide with these.
  • The current Settings module's model-options logic (cache control, reasoning levels per provider) is kept and moves behind the Loader, which passes the result to the Runtime as riffer model_options.
  • Settings are re-read on reload; a settings change is itself a reload trigger.

Enshrined in #123, with bullet 4 claimed here and implemented by #132, and the Interfaces row Files for the two settings.json files. Riffer::Rig::Settings (lib/riffer/rig/settings.rb) is reshaped into pure pieces the Loader composes: read(path) parses one file with symbol keys (a missing, malformed or non-object file reads as empty); merge(home, project) merges key by key, recursing into nested hashes, the project winning; Settings::Document is the frozen typed view of the core keys (model, reasoning, models, providers, disabled); model_options(model, reasoning) keeps the old cache-control and per-provider reasoning rules as a pure function; store_model(model, path:) writes onboarding's answer. DEFAULT_MODEL, Settings.model, Settings.pricing_for and the file-reading Settings.model_options(path:) are gone rather than kept as wrappers: the pre-#124 CLI reads a Document of the home file itself, takes RIFFER_MODEL over it, and with no model prints how to set one and exits 1; CodingAgent no longer reads settings at class load and gets its model and options from the CLI. Deviations. Two keys merge by their own rule: mcp through Riffer::Rig::Mcp.merge, a project server replacing the home one of the same name whole so home headers never reach a project url (Bundled: MCP), and extensions.disabled, whose lists add up (Bundled: disable). Of bullet 2, reload, sessions, extensions.autoload and tools are reserved and read by their tickets, and the providers block is still read and written by Credentials in the home file only, as the note under Providers: storage records. Bullet 3: the Runtime had no way to take model options, so it gains the keyword model_options: (default {}), handed to its Riffer::Agent::Config and kept through rebuild; a /model switch keeps the options built for the starting model until #129 re-derives them for the new provider.

Credentials

  • The Loader resolves every required field of the selected provider's recipe (env → auth.json → fallback Proc → host.ask(secret: true)), writes what the host answered to auth.json or the providers settings block, assigns the resolved values to Riffer.config by each field's name, and passes them to the Runtime as credentials:. The rules and file formats are in Providers.
  • Resolution happens once per build and again on reload; $VAR and !cmd references in auth.json are expanded at that moment and cached on the Runtime.
  • Switching provider with /model resolves the new provider's fields the same way through the Loader-installed command context.

Bullets 1 and 2 enshrined in #123; bullet 3 is #129's. Step 2 of Building a Runtime calls Credentials.resolve for the model's provider with the Loader's Env and the auth.json and settings.json under home:, so a pasted value is stored as Providers: resolution describes, then Credentials.apply to riffer_config:, and passes {provider => values} to the Runtime as credentials:. Resolution runs once per build, so $VAR and !cmd expand once and the values are cached on the Runtime; running it again on reload waits on #132. Deviation: a required field still missing after resolution raises Riffer::Rig::Loader::ConfigurationError rather than building a Runtime whose first request would fail.

Bullet 3 enshrined in #129: a /model switch resolves the new provider's fields through the command context the Loader-installed Runtime hands the command — Credentials.resolve with the context's host, so a pasted value is stored the same way, then Credentials.apply and Runtime#merge_credentials — after the missing-SDK flow of Providers, and refuses with one notify when a required field is still missing. The command resolves with the process defaults rather than the building Loader's keywords, the same deviation as /auth; details are in the note under Runtime: /model.

Reload

Scope

  • Reloaded: both rig.rb files, every local file they require or require_relative (under ~/.riffer or the project), settings.json in both scopes, auth.json, and trust status (a newly appearing project rig.rb goes through host.confirm).
  • Not reloaded: extension gems (riffer-rig-*), riffer-rig's own code (its Zeitwerk loader stays non-reloadable), riffer. Skills and AGENTS.md need no reload: their sections are evaluated per turn.

Triggers

  • Automatic: at every before_request boundary (between tool results and the next LLM call, not only at turn start) the Loader stats the tracked file set; any mtime change, or a tracked rig.rb appearing or disappearing, reloads. An agent that edits its own extension mid-turn sees the new tool on its very next request. A one-turn riffer -p benefits the same way.
  • Manual: /reload, a runtime command installed by the Loader; always reloads and re-discovers the file set.
  • No watcher thread, no listen dependency; the check runs on the prompting thread at a boundary where no handler is mid-flight, so no lock.
  • Core setting "reload": "auto" | "manual", default auto, project overrides home, also the Loader keyword reload:. Manual keeps /reload and Runtime#rebuild and drops the automatic check.

Mechanism

  1. On first load the Loader diffs $LOADED_FEATURES around loading each rig.rb; new entries under ~/.riffer or the project are the tracked files, gem paths dropped. The rig.rb files themselves are tracked too, so a newly added require is picked up from that reload on.
  2. On reload it deletes those entries from $LOADED_FEATURES and loads each rig.rb again, so plain require/require_relative re-execute with no author-side convention.
  3. Classes are reopened in place, not removed: edited and added methods take effect; deleted methods and renamed constants linger until restart (the one documented limit).
  4. Riffer::Rig.extension("name") records into the process registry keyed by name, so re-execution replaces the block rather than appending a duplicate.
  5. Settings, credentials and trust are re-read, then runtime.rebuild(extensions:, settings:).

Why not hot module replacement: Ruby's require keeps no dependency graph between files and extension blocks, and "later wins" ordering must be replayed anyway, so partial replacement would preserve only block locals at the cost of a second code path. Rejected: per-scope re-execution and TracePoint-based per-extension replacement.

Step 1 implemented in #126: on first load the Loader diffs $LOADED_FEATURES around each load of a rig.rb, keeps the entries under ~/.riffer or the project, tracks the rig.rb files themselves, and exposes the set as Loader#tracked_files. The rest of the list waits on #132, which enshrines this section.

Failure

  • The new registrar is built aside; nothing on the Runtime changes until it is complete. If a rig.rb itself raises, the reload is abandoned, the live registrar stays, the host gets one notify, and the mtime snapshot still advances so the check does not retry every request.
  • A single extension block failing follows the standard rule: skipped and reported, the rest swap in.
  • Errors go to the host only, never into the model's context.

Known limits

  • Reopened classes keep deleted methods and stale constants until restart.
  • Gem-packaged extensions do not reload.
  • Two Runtimes in one process share the process-level extension registry and providers; a reload in one does not rebuild the other.

Loader#reload(runtime, force: false) scrubs the tracked entries from $LOADED_FEATURES, loads the two rig.rb files again (re-discovering the tracked file set around each load, so a require added since the last load is tracked from that reload on), re-reads both settings.json files, re-resolves the current provider's credentials through Credentials.resolve (applied to riffer's config and merged into the Runtime), re-reads trust through the same trusted? ask, and calls runtime.rebuild(extensions:, settings:); /reload (lib/riffer/rig/commands/reload.rb) calls it with force: true and reports "Reloaded". The command is a core Command the Loader installs on the built Runtime through a new Runtime#install_command, so it survives every rebuild; user-facing text is in docs/RELOADING.md. Deviations. The parameter is the Runtime, not a session. reload also carries the change check the automatic trigger will call: with force: false it stats the tracked file set plus the two rig.rb paths and returns without rebuilding while they look as the last discovery left them, keeping the mtime snapshot on the Loader and advancing it after every attempt, failed ones included, so a failed reload does not retry every request; #133 installs the before_request check that calls it. Re-resolving credentials abandons the reload with one notify when a required field is still missing, like a raising rig.rb; the model is not re-selected, the SDK check does not run again, and the settings' model key is not read, per the rebuild contract of #120. The Loader remembers the strip keywords and the extensions: flag of its most recent build and reuses them, with the extensions the gem autoload recorded (gems are not re-executed, per Known limits), so a reload applies to that build's file set; a raise inside a re-executed rig.rb abandons (one notify, snapshot advanced) where a build would skip and continue. To honour the Failure list's "a single extension block failing … the rest swap in" against rebuild's stricter abort (#120's note), the Loader pre-runs the whole new list against throwaway registrars and drops each failure with one notify, so extension blocks run twice per reload; the aside registrar is discarded, so nothing registers twice. Because a command runs under the Runtime's busy claim, rebuild now refuses only a claim from another thread: a nested rebuild from the prompting thread's own command or hook proceeds (the deviation is recorded under Runtime: rebuild), which is also what the automatic check of #133 needs.

The remaining Triggers bullets enshrined in #133, with the Interfaces rows Settings keys owned here (reload) and the reload: keyword in the Strip and override row: the Loader installs an automatic reload check on the built Runtime through a new Runtime#install_reload_check (like install_command, so it survives every rebuild) unless the build's effective reload mode is manual, and the Runtime invokes it at both before_request boundaries — at the start of a turn, before the system message is refreshed and any handler runs, and after the last tool result of a round, before the before_request handlers run — so the check never overlaps a handler mid-flight and needs no lock. The check calls Loader#reload(runtime), whose change check does the gating, so a no-op costs the stat of the tracked file set alone; a turn that starts with a change waiting is served entirely by the reloaded registrar, because the check runs before the Runtime hands the turn to its agent. The mode is the core setting "reload", "auto" (default) or "manual", project overriding home, or the Loader keyword reload:, which wins over the setting; user-facing text is in docs/RELOADING.md and docs/CONFIGURATION.md. Deviations. The keyword defaults to nil rather than :auto — the row's :auto | :manual are the accepted values, and a default of :auto would pin the setting off — so the setting decides when the keyword is not given. The check is a callable the Runtime invokes itself rather than a registrar hook, so it needs no extension and cannot be replaced by one. The mode is decided when the Runtime is built: a build whose mode says manual installs no check, while an automatic session re-reads the setting inside the non-force reload, so a later flip to manual takes effect at the next boundary without a rebuild; a session built manual has no check to flip back with and picks up auto on the next build. The automatic entry point is the non-force reload, so a mode of manual also gates an embedder's own reload(runtime); force: true (/reload) always reloads. On "sees the new tool on its very next request": a mid-turn reload swaps the registrar at once and the turn's remaining requests keep the agent the turn started with — riffer's run loop binds one agent per run, so the edit reaches the model's next request from the following turn (an upstream candidate); "A one-turn riffer -p benefits the same way" holds for edits that land before the run starts. The check is installed on extensions: false builds too, where the tracked set is empty and it never fires.

Runtime store and resume

  • The Loader takes a store: collaborator, mints the Runtime id, appends entries as they land, restores snapshots, and prunes nothing. Hosts never see the store; they only choose which session to drive. Embedders without a Loader get no store.
  • Store contract: the RBS interface Riffer::Rig::Stores::_Store in sig/manual/, built the way Hosts::_Host is (a store is any object implementing all four; no base class, no runtime check): append(id, entry) (one entry hash, in order), read(id) (entries in order), list(cwd: nil) (header entries, optionally filtered by cwd), delete(id). A Rails host implements it over its own tables or skips the Loader and serialises the snapshot directly.
  • Entries: header (schema_version, id, cwd, created_at, model, riffer_rig_version, riffer_version, title = the first user prompt truncated to one line), message (a riffer message to_h, appended via runtime.on_message), model (each /model change), skill (each activation). Restore folds entries into a snapshot: last model wins, skill accumulates, message is the history. New entry types can be added without a schema bump.
  • Default store: Stores::JSONL at ~/.riffer/sessions/<cwd-slug>/<uuid>.jsonl, one entry per line, appended with File.write(mode: "a"). Zero dependencies, cat- and jq-able; a crash loses at most one line. The slug directory makes per-project listing a directory read, but the header's cwd is the truth, not the path. SQLite is not in core; it belongs in an extension gem such as riffer-rig-sqlite.
  • Restore reads the entries, folds them, and builds the Runtime with snapshot: plus today's extensions from rig.rb; the Runtime's restore rules (heal orphaned tail tool calls, saved model only with credentials, missing skills dropped) apply. Nothing blocks a resume.
  • Selection the Loader offers hosts: continue(cwd:) (most recently updated session whose header cwd matches, or nil), resume(id) (or nil if unknown), list(cwd:, all: false) for a picker, delete(id).
  • Policies: every Loader-built session is saved, including -p one-shots; opt out per run with store: nil (--no-save) or globally with "sessions": {"save": false}; keep forever, delete only from the picker; titles are the first prompt, no model call; scoped per cwd by default.
  • Deliberately not built: branching or a session tree, automatic pruning, generated or user-set titles, cross-project search, a riffer sessions subcommand.
