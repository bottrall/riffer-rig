Bundled

The coding toolkit and the three shared conventions, each an ordinary extension the user can disable or replace.

Scope

Seven named extensions shipped in the gem: read, write, edit, bash, agents_md, skills, mcp. Each is built only on the registrar seams; nothing here reaches into the Runtime. Files: lib/riffer/rig/bundled.rb (the list and Riffer::Rig.bundled), lib/riffer/rig/bundled/<name>.rb (one file per extension), lib/riffer/rig/tools/{read,write,edit,bash}.rb (the tool classes, kept where they are).

Depends on: Extensions. Depended on by: Loader (loads them first), Hosts (the default bundle every shipped host gets).

Decisions

What is bundled and why

  • Step 3 of the core-versus-extension rule: the coding toolkit, plus any convention at least two of pi, OpenCode, Claude Code and Codex already share. Today that is AGENTS.md, Agent Skills and an MCP client. Anything else (hooks, git context, models.dev catalog, web search on a provider without it) is third-party.
  • Bundled items are the default because a shell and file access are the most efficient way to get almost any task done; the prompt still claims no coding identity. A host can pass a different set.
  • The Loader loads all seven before any rig.rb, so user extensions can replace them. The order is read, write, edit, bash, agents_md, skills, mcp.
  • Provider-native tools (web search, and later code execution or file search) are not bundled; they are core, off by default, and switched on in settings (Providers: provider-native tools).

Bullets 1, 2 and 4 enshrined in #115: the coding toolkit ships as the bundled extensions read, write, edit and bash; the Runtime's base prompt claims no coding identity and a host passes whichever bundled extensions it wants in extensions:; provider-native tools are not among them. agents_md, skills and mcp join the bundle with their own tickets. Bullet 3 (the Loader loads all seven first) waits on #123, so the section is not yet marked enshrined.

read, write, edit, bash

The four tools keep their current behaviour, parameters and identifiers. Each is registered by its own bundled extension (Riffer::Rig.extension("read") { |rig| rig.tool Riffer::Rig::Tools::Read }) so it can be disabled or replaced one at a time. Each description gains one sentence of usage guidance, which is where the coding guidance from the old system prompt now lives:

ToolBehaviour keptGuidance sentence added to the description
readreturns a file with line numbers; offset/limit slice large files; missing file is a tool error"Read a file before editing it, and read rather than guess what a file contains."
writecreates or overwrites a file, making parent directories"Use this for new files or full rewrites; prefer edit for changes to an existing file."
editreplaces an exact string, unique by default, replace_all to replace every occurrence; ambiguous or missing match is a tool error"Prefer this over write for existing files; pass enough surrounding text to make old_string unique."
bashruns a command in the cwd in its own process group, combined stdout/stderr, exit status, per-call timeout, output truncated at 30,000 bytes"Use this for exploring and running things: ls, rg or grep, find, tests, git, package managers."
  • Tools never raise (riffer 0.43 contract); failures are tool errors the model sees.
  • bash reads the Runtime's cancel flag and kills its process group when set, instead of waiting for the message boundary.
  • Tools resolve relative paths against the Runtime's cwd, not Dir.pwd, so two Runtimes in one process can work in different directories.
  • A tool's name on --tools and tools: is its riffer identifier: read, write, edit, bash, and whatever identifier an extension tool declares.

The bullet "bash reads the Runtime's cancel flag" enshrined in #186: the Runtime hands its Riffer::Rig::Runtime::CancelFlag to tools as context[:cancel_flag]; bash polls it every 100 ms while the command runs, sends TERM to the process group and returns a tool error ending in [cancelled] (status 130). The rest of the section waits on the Bundled ticket, so the section is not yet marked enshrined.

Enshrined in #115, with the Interfaces rows Tool identifiers and Riffer::Rig.bundled(...) for the four tool names (the row's other three names arrive with #122 and the tickets after it). Each tool is registered by its own bundled extension in lib/riffer/rig/bundled/<name>.rb, and each description now ends with the table's guidance sentence, word for word. Each tool resolves relative paths against context[:cwd], which the Runtime puts in its agent's context beside the cancel flag; bash runs there too. Four deviations. The bundled extensions are built with Riffer::Rig::Extension.new and held as the constants Riffer::Rig::Bundled::Read, Write, Edit and Bash rather than recorded with Riffer::Rig.extension, so they stay out of the process registry and a user extension that shares a name cannot overwrite one. bash's guidance sentence replaces the sentence its description already had ("Use this for listing, searching (rg/grep/find), running tests, git, etc."), which said the same thing, instead of following it. A tool whose context carries no :cwd (the legacy CodingAgent, or a tool called directly) falls back to Dir.pwd, until #124 moves the terminal onto the Runtime and removes the fallback. And Riffer::Rig.bundled is defined in lib/riffer/rig.rb, not lib/riffer/rig/bundled.rb as Scope says: Zeitwerk loads bundled.rb only for the constant Riffer::Rig::Bundled, so that file holds the list (Riffer::Rig::Bundled::BY_NAME, in load order) and Riffer::Rig.bundled reads it. User-facing text is in docs/TOOLS.md.

AGENTS.md (agents_md)

  • Registers one prompt section, :agents_md. Every turn it reads ~/.riffer/AGENTS.md and <cwd>/AGENTS.md (whichever exist) and renders them framed as user-authored instructions that outrank the base norms, one block per file with its path, in that order. The current implementation's <project_instructions path="…"> wrapping is the seed; the framing sentence is new.
  • Because the section is a Proc evaluated per turn, an edited AGENTS.md takes effect on the next request with no reload.
  • Relative paths mentioned inside an AGENTS.md are the model's business; the extension does not resolve them.
  • Off via "extensions": {"disabled": ["agents_md"]} or the strip keyword agents_md: false (--no-agents-md).

Enshrined in #118, with the Interfaces rows Prompt sections (the :agents_md half), Files read (the AGENTS.md paths) and Riffer::Rig.bundled(...) for :agents_md, which joins the load order after bash. Riffer::Rig::Bundled::AgentsMd registers the :agents_md section; each turn it reads ~/.riffer/AGENTS.md then an AGENTS.md in every directory from the filesystem root down to runtime.cwd, whichever exist, and renders each as a <project_instructions path="…"> block with its absolute path, or nothing when neither exists. Relative paths inside a file are not resolved (#18 closes as decided against). User-facing text is in docs/INSTRUCTIONS.md and one line of the README's Configuration. Five deviations. The project half reads every ancestor of the cwd, not just the cwd, as Claude Code and pi do (Codex stops at the git root, OpenCode takes the nearest file only; the agents.md spec covers only per-package files chosen by the edited file, which is left for a later ticket): a monorepo's root file and a package's own both apply when running inside the package, and a file on both paths is read once. The framing sentence ("The user wrote the following instructions in AGENTS.md files, ordered from the most general to the one closest to the working directory. Follow them; where they conflict with the guidance above, they take precedence, and where they conflict with each other, the later file wins.") leads the section once, ahead of both blocks, rather than repeating inside each. The reading and rendering live in Riffer::Rig::Prompts::AgentsMd (lib/riffer/rig/prompts/agents_md.rb, beside tools/ as the home of what a bundled extension registers), with lib/riffer/rig/bundled/agents_md.rb only registering the section, because the legacy CodingAgent prompt and the terminal banner, which the terminal runs until #124, read the same two files; the old inline wrapping in CodingAgent is gone, and the terminal now gets the new framing too. ~/.riffer is resolved from Dir.home each turn rather than once at load. And of the Off bullet, what lands here is that agents_md is an ordinary extension: a host that leaves it out of extensions: gets no AGENTS.md. Reading extensions.disabled from settings and dropping a listed bundled extension is the Loader's (#123, per the note under Extensions: Settings seam), as are agents_md: false and --no-agents-md (#123, #124), which reference this bullet.

Agent Skills (skills)

  • Registers a Riffer::Skills::FilesystemBackend over ~/.riffer/skills and <cwd>/.skills through the skills seam, and one runtime command per discovered skill for activation. The command form today is /skill:<name> [args]; the reboot keeps it, and it is a runtime command so it works over ACP and headless too.
  • Activation reads the skill body through riffer's Skills::Context#read, sends it to the model as a user turn (ctx.prompt) wrapped as a skill, and emits skill_activated; the Loader's store records the name so a resumed Runtime re-activates by name.
  • The catalog the model sees is riffer's own second system message and is not touched. The :skills prompt section is reserved for anything rig adds about skills and is empty in v1, so a user can register their own :skills section without disabling the extension.
  • Off via "extensions": {"disabled": ["skills"]} or skills: false (--no-skills).

Enshrined in #121, with the Interfaces rows Commands (/skill:<name>), Prompt sections (the :skills half), Files read (the two skills directories) and Riffer::Rig.bundled(...) for :skills, which joins the load order after agents_md. Riffer::Rig::Bundled::Skills (lib/riffer/rig/bundled/skills.rb) registers, through rig.skills, a Riffer::Skills::FilesystemBackend over the project directories then ~/.agents/skills (riffer's rule: the earlier directory wins a name, and a missing one is skipped), and an empty :skills section that a later extension replaces by name. Activation reads the body with Skills::Context#read, which leaves riffer's activation state alone, so a skill the user runs stays in the model's catalog (#35, whose terminal half, the legacy REPL, switches to read here too). User-facing text is in docs/SKILLS.md and one line of the README's Configuration. Five deviations. Project skills come from .agents/skills in each directory from runtime.cwd up to the git root, the nearest directory at or above it holding a .git directory or file (a worktree or submodule has a file), or from <cwd>/.agents/skills alone outside a repository, following Codex, since .agents/skills is the cross-tool location that Codex, pi, OpenCode, Gemini CLI, Amp and Copilot read; the directory closest to the cwd wins a name, and any project skill wins over ~/.agents/skills, as a repo skill overrides a user skill in Codex. The home directory itself moves from the plan's ~/.riffer/skills to ~/.agents/skills, following Codex's user scope so personal skills are shared across tools; .riffer/skills is not read at all, anywhere. The walk is Riffer::Rig::Directories.up_to_repo_root (lib/riffer/rig/directories.rb), which shares its ancestors with the AGENTS.md walk, and runs each time the Runtime builds its agent config, so it follows runtime.cwd. Both directories come from one pure function, Riffer::Rig::Skills.directories(cwd) (lib/riffer/rig/skills.rb), rig's home for skills code as Prompts::AgentsMd is for AGENTS.md, which the legacy CodingAgent and the terminal banner's skill count also call, so they read the same directories as the Runtime. This supersedes <cwd>/.skills and ~/.riffer/skills in bullet 1, the Interfaces row Files read, and the skills/ entry of the Config dir row of Names. The skill:<name> commands are not registered by the extension but built by the Runtime, one per skill in riffer's resolved catalog, as core commands (Riffer::Rig::Commands::Skill, extension core) listed after model and before every extension's, which is how Extensions: commands bullet 3 already lists skill activation: a registrar block cannot see the Runtime's cwd, so it cannot discover the project's skills, and this way a skill from any extension's source gets a command too; a later extension's command of the same name still replaces one. "Wrapped as a skill" uses riffer's adapter, <skill_content name="…">, the tag riffer's catalog instructions tell the model to look for before activating, rather than the seed REPL's <skill>; the command's args follow the block after a blank line. skill_activated reaches the run_command block through a new ctx.emit(event) on the command context, ahead of the turn's events. And bullet 2's "the Loader's store records the name" holds for the model's own activations only: a snapshot's skills is riffer's activated list, which a user-run skill leaves untouched (its body is already in the history as a user turn), and a model switch or rebuild now carries that list to the new agent as a restore does. Of bullet 4, what lands here is that skills is an ordinary extension a host can leave out; extensions.disabled, skills: false and --no-skills are the Loader's and Terminal's (#123, #124).

MCP client (mcp)

  • Registers, through the rig.mcp seam, every server declared under the core settings key "mcp": {"servers": {"<name>": {"command": "…", "args": […]}}}, home then project, project overriding by name. Stdio servers only; that is the shape the seam takes and the shape the ACP mcpServers parameter maps to.
  • Extensions declare servers of their own with the same seam; this extension is only the settings-driven convention.
  • Server tools appear to the model with riffer's MCP tool naming; they are not on the four-tool identifier list and are not filtered by --tools unless named.
  • On reload, a server whose name, command and args are unchanged keeps its connection; others restart. Runtime#close stops them all.
  • Off via "extensions": {"disabled": ["mcp"]}.

Enshrined in #122, with the Interfaces rows Settings keys (mcp.servers) and Riffer::Rig.bundled(...) for :mcp, which joins the load order after skills, last. Riffer::Rig::Bundled::Mcp reads mcp.servers from its settings namespace and calls rig.mcp(name, url:, headers:) once per server, headers defaulting to none and sent as written; an entry without a url fails the extension with a KeyError, reported as a load error. Riffer::Rig::Mcp.merge(home, project) merges two mcp hashes by server name, a project server replacing the home one of the same name whole. As bullet 1 intends, the servers are backed by riffer's own MCP client: the Runtime registers each one with Riffer::Mcp.register(name:, endpoint:, tags:, discovery_headers:) under a tag unique to the Runtime (riffer_rig_<id>) and adds that tag to its agent config with add_mcp(tag, progressive: false), the use_mcp of a per-instance config, so the agent sees only its own servers and each tool directly under riffer's MCP naming, <server>__<tool>. A rebuild does not register again a server whose name, url and headers are unchanged, registers a changed one again (riffer replaces and retires the earlier registration) and unregisters one no longer declared; Runtime#close unregisters them all. A server that cannot be registered (riffer's Manifest rejects a URL that is not HTTPS, or tool discovery fails, which riffer's default sequential discovery_runner raises from register itself) is reported through notify at :error ("MCP server NAME failed to register: …") and skipped, at construction and on rebuild alike. User-facing text is in docs/MCP.md, with the mcp key in docs/CONFIGURATION.md and the seam in docs/EXTENSIONS.md. Deviations. At the maintainer's request stdio, bullet 1's only transport, is dropped for HTTPS servers, riffer's only one: the seam is rig.mcp(name, url:, headers: {}) and a mcp.servers entry is {url, headers}, and an ACP client's stdio mcpServers have nothing to map to. Bullet 3's "not filtered by --tools unless named" is now not filtered at all: riffer resolves MCP tools inside the agent, after tools_config, so the tools: allowlist never sees them, and the issue's allowlist test asserts that instead. riffer's registry is process-wide and keyed by server name, so two Runtimes in one process that declare the same name replace each other's registration; a Runtime never unregisters a registration that has since been replaced. Both gaps are marked in code as upstream candidates; the HTTPS-only manifests are recorded here and in docs/MCP.md, not in code. With no process or connection of rig's own, bullet 4's "keeps its connection" becomes "is not registered again", and riffer's client sends each request without MCP's initialize handshake, so a server that requires a session is out of reach. riffer declares no dependency on what its MCP client loads, so the gem adds mcp (~> 1.6), faraday (~> 2.14) and, for servers that answer with an SSE stream, event_stream_parser (~> 1.0). The Runtime takes the registry as a new constructor keyword, mcp_registry: (default Riffer::Mcp). The home-then-project merge is a function the Loader (#123) calls when it merges the two settings files, since the Runtime takes one merged settings: hash; until then the terminal uses no MCP servers. To read mcp.servers while its block runs, an extension block gets its settings namespace as rig.settings (given values over the defaults declared so far), and the Registrar's internal reader of declared defaults is now declared_settings. mcp is a core settings key, so the Runtime exempts the bundled extension, and only it, from the core-key name collision. An MCP server is a registration like a tool, so a later declaration of the same name replaces the earlier one and is reported as "Extension LATER replaces MCP server NAME from EARLIER". The Off bullet is, as for agents_md, only that mcp is an ordinary extension a host can leave out of extensions:; reading extensions.disabled is the Loader's (#123). This is the last Bundled topic, #121 having landed :skills; the page stays whole as the record rather than going, per the decision after #104.

Disable and replace

  • Disable with "extensions": {"disabled": [...]} in either settings scope; the lists merge. A disabled bundled extension is simply not passed to Runtime.new.
  • Replace by registering under the same identifier from a later extension: a tool with identifier 'bash', a command named model, a prompt section :agents_md. Later wins; the override is logged at info level through notify. Nothing is deregistered, so the original is still reachable as Riffer::Rig.bundled(:bash).
  • The strip keywords (extensions: false, skills: false, agents_md: false, tools: [...]) are Loader concerns and are listed under Loader: interfaces. extensions: false strips rig.rb extensions only; the bundle stays.

Bullet 2 (Replace) enshrined in #115: each registrar keys its tools by identifier, and the Runtime merges the registrars in load order, so a later tool, command or prompt section under the same name replaces the earlier one in its place. Every replacement across extensions is reported through the host's notify at level :info as "Extension LATER replaces KIND NAME from EARLIER" (KIND is tool, command or prompt section), and so reaches the stream as a notify event; a name registered twice within one extension is replaced silently, as before. Riffer::Rig.bundled(:bash) still returns the original. Bullets 1 and 3 wait on #123, so the section is not yet marked enshrined.
