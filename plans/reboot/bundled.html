Bundled

The coding toolkit and the three shared conventions, each an ordinary extension the user can disable or replace.

Scope

Seven named extensions shipped in the gem: read, write, edit, bash, agents_md, skills, mcp. Each is built only on the registrar seams; nothing here reaches into the Runtime. Files: lib/riffer/rig/bundled.rb (the list and Riffer::Rig.bundled), lib/riffer/rig/bundled/<name>.rb (one file per extension), lib/riffer/rig/tools/{read,write,edit,bash}.rb (the tool classes, kept where they are).

Depends on: Extensions. Depended on by: Loader (loads them first), Hosts (the default bundle every shipped host gets).

Decisions

What is bundled and why

  • Step 3 of the core-versus-extension rule: the coding toolkit, plus any convention at least two of pi, OpenCode, Claude Code and Codex already share. Today that is AGENTS.md, Agent Skills and an MCP client. Anything else (hooks, git context, models.dev catalog, web search on a provider without it) is third-party.
  • Bundled items are the default because a shell and file access are the most efficient way to get almost any task done; the prompt still claims no coding identity. A host can pass a different set.
  • The Loader loads all seven before any rig.rb, so user extensions can replace them. The order is read, write, edit, bash, agents_md, skills, mcp.
  • Provider-native tools (web search, and later code execution or file search) are not bundled; they are core, off by default, and switched on in settings (Providers: provider-native tools).

Bullets 1, 2 and 4 enshrined in #115: the coding toolkit ships as the bundled extensions read, write, edit and bash; the Runtime's base prompt claims no coding identity and a host passes whichever bundled extensions it wants in extensions:; provider-native tools are not among them. agents_md, skills and mcp join the bundle with their own tickets. Bullet 3 (the Loader loads all seven first) waits on #123, so the section is not yet marked enshrined.

read, write, edit, bash

The four tools keep their current behaviour, parameters and identifiers. Each is registered by its own bundled extension (Riffer::Rig.extension("read") { |rig| rig.tool Riffer::Rig::Tools::Read }) so it can be disabled or replaced one at a time. Each description gains one sentence of usage guidance, which is where the coding guidance from the old system prompt now lives:

ToolBehaviour keptGuidance sentence added to the description
readreturns a file with line numbers; offset/limit slice large files; missing file is a tool error"Read a file before editing it, and read rather than guess what a file contains."
writecreates or overwrites a file, making parent directories"Use this for new files or full rewrites; prefer edit for changes to an existing file."
editreplaces an exact string, unique by default, replace_all to replace every occurrence; ambiguous or missing match is a tool error"Prefer this over write for existing files; pass enough surrounding text to make old_string unique."
bashruns a command in the cwd in its own process group, combined stdout/stderr, exit status, per-call timeout, output truncated at 30,000 bytes"Use this for exploring and running things: ls, rg or grep, find, tests, git, package managers."
  • Tools never raise (riffer 0.43 contract); failures are tool errors the model sees.
  • bash reads the Runtime's cancel flag and kills its process group when set, instead of waiting for the message boundary.
  • Tools resolve relative paths against the Runtime's cwd, not Dir.pwd, so two Runtimes in one process can work in different directories.
  • A tool's name on --tools and tools: is its riffer identifier: read, write, edit, bash, and whatever identifier an extension tool declares.

The bullet "bash reads the Runtime's cancel flag" enshrined in #186: the Runtime hands its Riffer::Rig::Runtime::CancelFlag to tools as context[:cancel_flag]; bash polls it every 100 ms while the command runs, sends TERM to the process group and returns a tool error ending in [cancelled] (status 130). The rest of the section waits on the Bundled ticket, so the section is not yet marked enshrined.

Enshrined in #115, with the Interfaces rows Tool identifiers and Riffer::Rig.bundled(...) for the four tool names (the row's other three names arrive with #122 and the tickets after it). Each tool is registered by its own bundled extension in lib/riffer/rig/bundled/<name>.rb, and each description now ends with the table's guidance sentence, word for word. Each tool resolves relative paths against context[:cwd], which the Runtime puts in its agent's context beside the cancel flag; bash runs there too. Four deviations. The bundled extensions are built with Riffer::Rig::Extension.new and held as the constants Riffer::Rig::Bundled::Read, Write, Edit and Bash rather than recorded with Riffer::Rig.extension, so they stay out of the process registry and a user extension that shares a name cannot overwrite one. bash's guidance sentence replaces the sentence its description already had ("Use this for listing, searching (rg/grep/find), running tests, git, etc."), which said the same thing, instead of following it. A tool whose context carries no :cwd (the legacy CodingAgent, or a tool called directly) falls back to Dir.pwd, until #124 moves the terminal onto the Runtime and removes the fallback. And Riffer::Rig.bundled is defined in lib/riffer/rig.rb, not lib/riffer/rig/bundled.rb as Scope says: Zeitwerk loads bundled.rb only for the constant Riffer::Rig::Bundled, so that file holds the list (Riffer::Rig::Bundled::BY_NAME, in load order) and Riffer::Rig.bundled reads it. User-facing text is in docs/TOOLS.md.

AGENTS.md (agents_md)

  • Registers one prompt section, :agents_md. Every turn it reads ~/.riffer/AGENTS.md and <cwd>/AGENTS.md (whichever exist) and renders them framed as user-authored instructions that outrank the base norms, one block per file with its path, in that order. The current implementation's <project_instructions path="…"> wrapping is the seed; the framing sentence is new.
  • Because the section is a Proc evaluated per turn, an edited AGENTS.md takes effect on the next request with no reload.
  • Relative paths mentioned inside an AGENTS.md are the model's business; the extension does not resolve them.
  • Off via "extensions": {"disabled": ["agents_md"]} or the strip keyword agents_md: false (--no-agents-md).

Enshrined in #118, with the Interfaces rows Prompt sections (the :agents_md half), Files read (the two AGENTS.md paths) and Riffer::Rig.bundled(...) for :agents_md, which joins the load order after bash. Riffer::Rig::Bundled::AgentsMd registers the :agents_md section; each turn it reads ~/.riffer/AGENTS.md then <runtime.cwd>/AGENTS.md, whichever exist, and renders each as a <project_instructions path="…"> block with its absolute path, or nothing when neither exists. Relative paths inside a file are not resolved (#18 closes as decided against). User-facing text is in docs/INSTRUCTIONS.md and one line of the README's Configuration. Four deviations. The framing sentence ("The user wrote the following instructions in AGENTS.md files. Follow them; where they conflict with the guidance above, they take precedence.") leads the section once, ahead of both blocks, rather than repeating inside each. The reading and rendering live in Riffer::Rig::AgentsMd (lib/riffer/rig/agents_md.rb), with lib/riffer/rig/bundled/agents_md.rb only registering the section, because the legacy CodingAgent prompt and the terminal banner, which the terminal runs until #124, read the same two files; the old inline wrapping in CodingAgent is gone, and the terminal now gets the new framing too. ~/.riffer is resolved from Dir.home each turn rather than once at load. And of the Off bullet, what lands here is that agents_md is an ordinary extension: a host that leaves it out of extensions: gets no AGENTS.md. Reading extensions.disabled from settings and dropping a listed bundled extension is the Loader's (#123, per the note under Extensions: Settings seam), as are agents_md: false and --no-agents-md (#123, #124), which reference this bullet.

Agent Skills (skills)

  • Registers a Riffer::Skills::FilesystemBackend over ~/.riffer/skills and <cwd>/.skills through the skills seam, and one runtime command per discovered skill for activation. The command form today is /skill:<name> [args]; the reboot keeps it, and it is a runtime command so it works over ACP and headless too.
  • Activation reads the skill body through riffer's Skills::Context#read, sends it to the model as a user turn (ctx.prompt) wrapped as a skill, and emits skill_activated; the Loader's store records the name so a resumed Runtime re-activates by name.
  • The catalog the model sees is riffer's own second system message and is not touched. The :skills prompt section is reserved for anything rig adds about skills and is empty in v1, so a user can register their own :skills section without disabling the extension.
  • Off via "extensions": {"disabled": ["skills"]} or skills: false (--no-skills).

MCP client (mcp)

  • Registers, through the rig.mcp seam, every server declared under the core settings key "mcp": {"servers": {"<name>": {"command": "…", "args": […]}}}, home then project, project overriding by name. Stdio servers only; that is the shape the seam takes and the shape the ACP mcpServers parameter maps to.
  • Extensions declare servers of their own with the same seam; this extension is only the settings-driven convention.
  • Server tools appear to the model with riffer's MCP tool naming; they are not on the four-tool identifier list and are not filtered by --tools unless named.
  • On reload, a server whose name, command and args are unchanged keeps its connection; others restart. Runtime#close stops them all.
  • Off via "extensions": {"disabled": ["mcp"]}.

Disable and replace

  • Disable with "extensions": {"disabled": [...]} in either settings scope; the lists merge. A disabled bundled extension is simply not passed to Runtime.new.
  • Replace by registering under the same identifier from a later extension: a tool with identifier 'bash', a command named model, a prompt section :agents_md. Later wins; the override is logged at info level through notify. Nothing is deregistered, so the original is still reachable as Riffer::Rig.bundled(:bash).
  • The strip keywords (extensions: false, skills: false, agents_md: false, tools: [...]) are Loader concerns and are listed under Loader: interfaces. extensions: false strips rig.rb extensions only; the bundle stays.

Bullet 2 (Replace) enshrined in #115: each registrar keys its tools by identifier, and the Runtime merges the registrars in load order, so a later tool, command or prompt section under the same name replaces the earlier one in its place. Every replacement across extensions is reported through the host's notify at level :info as "Extension LATER replaces KIND NAME from EARLIER" (KIND is tool, command or prompt section), and so reaches the stream as a notify event; a name registered twice within one extension is replaced silently, as before. Riffer::Rig.bundled(:bash) still returns the original. Bullets 1 and 3 wait on #123, so the section is not yet marked enshrined.
